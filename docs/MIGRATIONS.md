# Database Migrations with Alembic

This project uses Alembic to manage all database schema changes. Manual `ALTER TABLE` statements are no longer used.

---

## Prerequisites

Activate the backend virtual environment before running any Alembic commands:

```powershell
cd C:\lslp\backend
venv\Scripts\activate
```

All commands below assume you are in `C:\lslp\backend` with the venv active.

---

## Adding a column (or any schema change)

### 1. Edit the SQLAlchemy model

Open the relevant file in `app/models/` and add the column. For example, adding a nullable date column to visits:

```python
# app/models/visit.py
from sqlalchemy import Column, Date
# ...
class Visit(Base):
    # ... existing columns ...
    follow_up_date = Column(Date)
```

If the column should appear in API responses, also add it to the Pydantic schema in `app/schemas/`.

### 2. Generate the migration

```powershell
alembic revision --autogenerate -m "add_follow_up_date_to_visits"
```

This creates a new file in `alembic/versions/`. The filename includes a revision hash and your description.

### 3. Read the migration before applying it

**This step is not optional.** Open the generated file and read the `upgrade()` and `downgrade()` functions. Autogenerate is useful but imperfect:

- It **does not detect** renamed columns (it will drop the old one and create a new one, destroying data).
- It **does not detect** changes to column data (e.g., populating a new NOT NULL column with defaults).
- It **occasionally proposes destructive changes** like dropping indexes or constraints that should stay.
- It may generate no-op changes for type differences that are equivalent in PostgreSQL (e.g., `String` vs `Text`).

If the migration looks wrong, edit it by hand. The autogenerated comments (`# ### commands auto generated by Alembic ###`) are just markers — you can freely modify the code between them.

### 4. Apply the migration

```powershell
alembic upgrade head
```

This runs all pending migrations. To apply just one step:

```powershell
alembic upgrade +1
```

### 5. Verify

Confirm the column exists and the app still starts:

```powershell
python -c "from main import app; print('OK')"
```

## Rolling back a migration

To undo the most recent migration:

```powershell
alembic downgrade -1
```

To roll back to a specific revision:

```powershell
alembic downgrade <revision_hash>
```

You can find revision hashes with:

```powershell
alembic history
```

Rolling back removes the schema change but does **not** restore any data that was dropped.

---

## Checking current state

```powershell
# What revision is the database at?
alembic current

# Full migration history
alembic history --verbose
```

---

## Common mistakes to avoid

1. **Never run `ALTER TABLE` manually.** If you change the database outside Alembic, the migration history becomes wrong and every future migration will fail or produce incorrect results.

2. **Never apply a migration without reading it.** The autogenerate sees type differences between the model and database, but it cannot always tell which direction is correct. A migration that drops a column because the model was wrong will destroy data.

3. **Never delete a migration file that has been applied.** Alembic tracks which migrations have run. Deleting an applied migration corrupts the history.

4. **Always keep models in sync with the database.** If someone runs a manual SQL change (don't), update the model to match before generating the next migration — otherwise autogenerate will try to undo their change.

## How it works

- `alembic.ini` — configuration file; the database URL is loaded from `.env` at runtime (not hardcoded).
- `alembic/env.py` — imports all SQLAlchemy models so autogenerate can compare them against the live database.
- `alembic/versions/` — one Python file per migration, chained by revision IDs.
- `alembic_version` table in the database — stores the current revision hash.
